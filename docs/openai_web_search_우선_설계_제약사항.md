# OpenAI 웹 검색 우선 설계 시 현재 AI 검색 하네스의 제약사항

> 구현 상태(2026-08-05): 이 문서의 Phase 1 권고 중 원 질문·구조화 검색 맥락
> 전달, `tool_choice="required"`, 한국 위치 힌트, live access 명시, 전체 검색
> source 요청, 근거 문서 범위 확대, 질문 단위 통합 검색, 라운드당 URL 후보
> 2개, Firecrawl 오류 재시도 1회 상한, Firecrawl 원문 기반 질문 관련성·독립
> 출처·필요 증거 범주 평가와 증거 공백 후속 검색까지 적용되었다.

## 결론

OpenAI의 기본 웹 검색 기능을 가장 우선하여 활용하려는 관점에서 보면, 현재 AI 검색 하네스는 웹 검색의 자율성과 검색 범위를 상당히 제약한다.

가장 큰 문제는 개별 검색어보다도 **출처별로 미리 만든 검색어를 제공하고 검색시키는 전체 구조**다. 현재 구현은 OpenAI가 검색 전략 전체를 설계하는 방식이 아니라, 코드가 출처와 최초 검색어를 정하고 AI가 그 범위 안에서 재검색하는 방식에 가깝다.

OpenAI 웹 검색을 실질적인 1순위 수집 수단으로 사용하려면 검색어 생성, 출처 탐색, 정보 공백 판단을 질문 단위로 AI가 수행하고, 애플리케이션 코드는 비용, 출처 신뢰도, 원문 검증과 종료 조건을 통제하는 구조가 더 적합하다.

## 현재 실행 구조

현재 AI 검색 하네스의 실행 흐름은 다음과 같다.

```text
출처별 검색어 사전 생성
  → OpenAI 웹 검색
  → 실제 URL citation 추출
  → Firecrawl 원문 스크랩
  → AI가 이번 검색의 충분성 판단
      ├─ 충분함 → 종료
      └─ 부족함 → AI가 후속 검색어 생성
                    → 최대 3라운드 반복
```

관련 구현:

- `sources/collectors/ai_search_harness.py`
- `core/source_planner/query_strategy.py`
- `sectors/sk_broadband/adapter/collector/__init__.py`

## 1. 검색어와 질문 맥락의 제약

### 1.1 OpenAI가 검색어를 설계하기 전에 코드가 검색어를 확정한다

현재 하네스는 `build_source_search_terms()`로 검색어를 먼저 만든다.

```python
terms = build_source_search_terms(source, question_keywords)
query = " ".join(...)
```

그 후 모델에는 다음과 같은 형태로 전달한다.

```text
Search query: SK브로드밴드 IPTV 경쟁력 KT 지니TV ...
```

따라서 모델이 원 질문을 보고 검색 전략을 처음부터 설계하는 것이 아니라, 이미 조립된 검색 문자열을 출발점으로 사용한다.

이 방식에는 다음과 같은 문제가 있다.

- 엔티티 추출이 잘못되면 검색 전체가 잘못된 방향으로 시작될 수 있다.
- 많은 단어를 하나의 문자열로 합쳐 최초 검색이 지나치게 구체적일 수 있다.
- 동일한 의미의 브랜드와 제품명이 중복될 수 있다.
- `현황`, `원인`, `대응` 같은 질문 목적이 실제 기사에서 쓰이지 않는 표현으로 섞일 수 있다.
- 시장 전체에 대한 질문에서도 특정 기업명이 검색 결과를 지배할 수 있다.
- AI가 더 적합한 최초 검색어를 만들 수 있어도 코드가 만든 검색어에 앵커링될 수 있다.

후속 라운드부터는 AI가 검색어를 변경할 수 있지만, 첫 번째 검색에서 결과가 어느 정도 확보되면 1라운드에서 바로 종료될 수 있다. 이 경우 AI의 검색 전략 설계 능력을 거의 사용하지 못한다.

### 1.2 원 질문 전체가 아닌 압축된 키워드만 전달한다

현재 검색 호출에는 다음 맥락이 충분히 전달되지 않는다.

- 사용자의 원 질문
- 질문의 보고 목적
- 회사 현황인지 시장 전체인지에 대한 관점
- 어떤 결정을 지원해야 하는지
- 필요한 증거 종류
- 대상 독자
- 이미 확보한 증거와 아직 부족한 증거

대신 검색 문자열과 현재 출처의 이름 및 역할을 중심으로 전달한다.

다음 질문들은 비슷한 단어를 사용하지만 필요한 검색 전략과 출처가 다르다.

```text
SK브로드밴드의 AI 미디어 전략 현황
국내 AI 미디어 시장에서 SK브로드밴드의 경쟁력
SK브로드밴드 AI 미디어 전략의 문제 원인
경영진이 판단해야 할 AI 미디어 투자 기회
```

따라서 검색 입력에는 단순 키워드가 아니라 원 질문과 구조화된 질문 맥락이 함께 전달되어야 한다.

## 2. 출처별 실행 구조의 제약

### 2.1 웹 전체를 검색하면서 출처 단위로 반복 호출한다

현재는 선택된 출처마다 AI 검색 하네스를 별도로 실행한다.

```text
SK브로드밴드 뉴스룸 슬롯 → 웹 전체 검색
전자신문 슬롯             → 웹 전체 검색
경쟁사 뉴스룸 슬롯         → 웹 전체 검색
```

하네스는 현재 슬롯의 도메인으로 검색 범위를 제한하지 않는다. 따라서 여러 슬롯에서 동일한 기사나 동일한 출처를 반복 발견할 수 있다.

이 구조에서 발생할 수 있는 문제는 다음과 같다.

- 동일하거나 유사한 웹 검색을 여러 번 수행한다.
- 동일 URL을 서로 다른 슬롯에서 반복 발견할 수 있다.
- OpenAI 웹 검색 비용이 중복될 수 있다.
- 현재 출처 슬롯의 이름이 모델 판단을 불필요하게 편향할 수 있다.
- 질문 전체에서 부족한 증거보다 현재 슬롯을 채우는 데 집중할 수 있다.
- 출처 다양성을 질문 전체 수준에서 최적화하기 어렵다.

OpenAI 웹 검색을 우선하려면 출처별 검색보다 질문별 통합 검색 세션이 더 자연스럽다.

## 3. OpenAI 웹 검색 호출 설정의 제약

### 3.1 `tool_choice="auto"`라서 검색 실행이 보장되지 않는다

현재 코드는 다음 설정을 사용한다.

```python
tools=[{"type": "web_search", ...}],
tool_choice="auto",
```

OpenAI 공식 문서에 따르면 `tool_choice="auto"`에서는 모델이 웹 검색을 사용하지 않을 수 있다. 검색을 반드시 실행해야 한다면 `required` 또는 특정 웹 검색 도구 선택을 사용해야 한다.

- 공식 문서: <https://developers.openai.com/api/docs/guides/tools-web-search>

OpenAI 웹 검색을 최우선으로 사용한다면 `tool_choice="required"`가 현재 의도에 더 부합한다.

### 3.2 기본 모델이 `gpt-4o`로 고정되어 있다

현재 기본 모델은 다음과 같다.

```python
_HARNESS_DEFAULT_MODEL = "gpt-4o"
```

현재 OpenAI 공식 문서는 신규 통합에 Responses API의 `web_search` 도구 사용을 권장하며, 최신 예시는 GPT-5 계열을 기준으로 한다. 공식 모델 목록에서도 GPT-4o는 deprecated 모델로 분류되어 있다.

- 웹 검색 가이드: <https://developers.openai.com/api/docs/guides/tools-web-search>
- 모델 목록: <https://developers.openai.com/api/docs/models/all>

웹 검색을 핵심 기능으로 운영하려면 현재 지원되는 모델로 전환한 뒤 검색 품질, 비용과 지연시간을 다시 평가해야 한다.

### 3.3 한국 지역 정보가 전달되지 않는다

OpenAI 웹 검색은 `user_location`을 지원하지만 현재 하네스에는 설정되어 있지 않다.

SK브로드밴드처럼 한국 시장 중심의 서비스를 검색할 때는 다음과 같은 대략적인 위치 정보가 유용할 수 있다.

```python
"user_location": {
    "type": "approximate",
    "country": "KR",
    "city": "Seoul",
    "region": "Seoul",
}
```

위치 정보가 없다고 한국 검색 결과가 나오지 않는 것은 아니지만, 지역성이 강한 질문에서 한국 결과를 우선할 신호가 빠져 있다.

### 3.4 검색 도메인 필터를 활용하지 않는다

현재는 웹 전체 검색만 사용하며 `allowed_domains` 또는 `blocked_domains`를 사용하지 않는다.

OpenAI의 `web_search` 도구는 도메인 필터를 지원한다.

- `allowed_domains`
- `blocked_domains`

다만 모든 검색을 등록 도메인으로 제한하면 새로운 고품질 출처를 발견하기 어렵다. 검색 단계별로 선택적으로 적용하는 편이 적절하다.

```text
1차 검색: 웹 전체에서 폭넓게 탐색
2차 검색: 공식 발표가 부족하면 공식 도메인 우선
3차 검색: 규제 근거가 부족하면 정부·규제기관 도메인 제한
4차 검색: 사용자 반응이 필요하면 커뮤니티 출처를 별도 허용
```

### 3.5 전체 검색 출처 목록을 요청하지 않는다

OpenAI 웹 검색은 다음 옵션으로 검색 과정에서 고려한 전체 출처 목록을 응답에 포함할 수 있다.

```python
include=["web_search_call.action.sources"]
```

현재 하네스는 최종 응답의 `url_citation`만 수집한다.

Citation만 신뢰하는 것은 URL 환각 방지 측면에서는 안전하지만, 모델이 검색 과정에서 검토했으나 최종 문장에 인용하지 않은 후보는 모두 사라진다. 검색 후보 수집이 목적이라면 전체 sources를 받은 뒤 실제 기사 URL을 별도로 평가하는 방식이 recall 측면에서 유리할 수 있다.

## 4. 검색 깊이와 종료 조건의 제약

### 4.1 최대 3라운드로 고정되어 있다

```python
max_rounds = 3
```

대부분의 질문에는 합리적인 상한이지만, 다음과 같은 복합 질문에는 부족할 수 있다.

```text
시장 현황 + 경쟁사 + 규제 + 이용자 반응 + 재무 실적
```

반대로 단순한 공식 발표 검색에는 3라운드가 과할 수 있다.

고정 라운드 수 외에 다음 조건을 함께 고려해야 한다.

- 필요한 증거 카테고리
- 독립 출처 수
- 출처 역할 다양성
- 남아 있는 정보 공백
- 최대 비용
- 최대 실행시간

### 4.2 문서 1건만 확보해도 성공할 수 있다

하네스의 기본 목표는 2건이지만, 모델이 `sufficient=true`를 반환하면 한 건만 확보해도 종료한다. SK브로드밴드 collector도 최소 한 건이면 해당 출처 수집을 성공으로 인정한다.

```text
목표: 2건
실제: 공식 뉴스룸 1건
AI 판단: sufficient=true
결과: 성공
```

경쟁력, 시장 현황 또는 원인 분석 질문에서는 단일 출처가 충분하지 않을 수 있다.

충분성은 단순 문서 수보다 다음 기준으로 판단해야 한다.

- 독립 출처가 2개 이상인가
- 공식 주장과 외부 분석이 모두 있는가
- 질문이 요구한 정보 범주를 채웠는가
- 특정 기업의 자체 발표에만 의존하지 않는가
- 경쟁사 비교 근거가 실제로 있는가

### 4.3 AI의 충분성 판단이 Firecrawl 성공 여부를 반영하지 못한다

AI는 citation을 보고 `sufficient=true`인지 판단한다. 하지만 그 뒤 Firecrawl 스크랩이 실패할 수 있다.

```text
OpenAI가 URL 2개 발견
  → OpenAI는 충분하다고 판단
  → Firecrawl이 URL 2개 스크랩
  → 일부 또는 전체 스크랩 실패
  → sufficient=true이므로 검색 종료
```

AI는 발견한 URL을 기준으로 충분하다고 판단하지만, 실제 파이프라인은 성공적으로 확보한 원문을 필요로 한다.

따라서 충분성 판단은 Firecrawl 수집이 끝난 뒤 성공한 문서 수와 증거 범위를 기준으로 다시 계산해야 한다.

### 4.4 스크랩에 실패한 URL의 제한적 재시도

Phase 1 초기 구현에서는 citation URL을 Firecrawl 호출 전에 처리 목록에 추가하고 재시도하지 않았다.

현재는 Firecrawl 호출 자체가 예외 또는 타임아웃으로 실패하면 같은 URL을 즉시 딱 한 번 더 호출한다. 두 번째 호출도 실패하면 이후 라운드에서 다시 시도하지 않는다. 정상 응답이지만 본문이 없거나 250자 미만인 품질 미달 응답은 일시적 호출 오류가 아니므로 재시도하지 않는다.

다음과 같이 상태를 구분하는 편이 안전하다.

```text
discovered_urls
successfully_scraped_urls
failed_scrape_urls
```

이 구분으로 일시적 호출 오류에는 복구 기회를 주면서도 URL 하나가 반복적으로 호출되는 상황을 막는다.

## 5. 프롬프트가 검색 범위를 제한하는 문제

### 5.1 뉴스 기사만 찾도록 제한한다

현재 시스템 프롬프트는 `currently-live news articles`를 찾도록 요구한다.

이로 인해 다음과 같은 자료가 검색 대상에서 제외될 수 있다.

- 기업 IR PDF
- 정부 정책 원문
- 규제기관 보도자료
- 통계 데이터 페이지
- 시장조사 보고서
- 기업 실적 발표 자료
- 기술 백서
- 공식 서비스 문서
- 학술 및 산업 보고서

TrendSparC의 목적이 산업 인텔리전스라면 뉴스 기사보다 질문에 필요한 근거 문서 전체를 검색 대상으로 삼는 것이 적절하다.

예시 프롬프트:

```text
Find the strongest currently accessible evidence relevant to the question,
including news articles, official announcements, regulatory documents,
IR materials, statistical reports, and industry analysis.
```

### 5.2 최신성 요구가 구체적이지 않다

현재 프롬프트는 `currently-live`라고 표현한다. 이는 URL이 현재 접근 가능하다는 의미에 가깝고 최근에 작성된 자료라는 의미는 아니다.

현재 검색 요청에는 다음 정보가 없다.

- 검색 기준일
- 원하는 기간
- 최근 12개월 같은 기간 조건
- 질문 목적별 허용 기간
- 최신 자료와 역사적 근거의 구분

따라서 최근 현황 질문에서도 오래된 기사가 검색될 수 있다.

검색 프롬프트에 기준 날짜와 기간을 명시하고, 수집 후 `published_at`을 사용해 다시 검증해야 한다.

## 6. 비용과 호출량의 제약

Phase 2 적용 전에는 선택된 일반 웹 출처마다 최대 3번 OpenAI 웹 검색을 호출할 수 있었다.

```text
출처 최대 6개 × 출처당 최대 3라운드 = 최대 18개 검색 라운드
```

Phase 2 적용 후 SK브로드밴드 AI 검색 경로는 질문당 하나의 검색 세션만 실행한다.

```text
질문당 최대 3라운드
라운드당 URL 후보 최대 2개
질문당 Firecrawl 스크랩 최대 12회
URL당 최초 스크랩 1회, 예외·타임아웃 실패 시 딱 한 번 재시도
```

각 citation을 Firecrawl로 다시 스크랩하므로 OpenAI 웹 검색 비용뿐 아니라 Firecrawl 비용도 발생한다.

현재 코드는 한 라운드에서 Firecrawl에 넘기는 citation을 최대 2개로 선제 제한한다. 각 라운드 직후 실제 Firecrawl 원문의 관련 구간을 GPT Structured Outputs로 평가한다. 질문 관련 원문 2개 이상, 독립 출처 2곳 이상, 모든 `information_needs` 충족 조건을 동시에 만족해야 종료한다. 부족한 증거 범주는 GPT가 제시한 후속 검색어로 다음 라운드에 전달한다. 최대 3라운드 안에 조건을 충족하지 못하면 수집 단계를 성공 처리하지 않는다. 최대 6개 원문까지 보관하며, Firecrawl 예외·타임아웃 URL은 한 번만 추가 호출한다.

따라서 다음 예산을 분리해 관리해야 한다.

- 질문당 OpenAI 검색 라운드 수
- 질문당 citation 후보 수
- 질문당 Firecrawl 스크랩 호출 수
- 출처별 최대 문서 수
- 질문당 총 실행시간
- 질문당 최대 비용

## 7. 유지할 가치가 있는 현재 안전장치

현재 구현의 모든 제약이 나쁜 것은 아니다. 다음 안전장치는 유지할 가치가 있다.

- 실제 `url_citation` annotation이 없는 URL은 사용하지 않는다.
- OpenAI 응답의 일반 텍스트에 포함된 URL은 신뢰하지 않는다.
- Firecrawl로 실제 원문을 확보한 뒤 분석한다.
- 본문이 250자 미만이면 제외한다.
- 동일 URL을 중복 결과로 반환하지 않는다.
- 등록되지 않은 출처의 신뢰도 등급을 추측하지 않는다.
- 한 출처의 실패가 전체 수집을 중단시키지 않는다.
- 후단 분석기가 `relevant_to_question`을 다시 판단한다.
- 최종 사실과 수치는 원문 근거를 통해 검증한다.

## 8. 권장 아키텍처

OpenAI 웹 검색을 실질적인 1순위로 사용하려면 다음 구조가 적합하다.

```text
원 질문
  → 질문·목적·관점·필요 증거를 OpenAI에 구조화해 전달
  → OpenAI가 최초 검색 전략과 검색어 설계
  → 웹 전체 통합 검색
  → 실제 citation 및 source 후보 확보
  → Firecrawl 원문 수집
  → 수집 성공 문서를 기준으로 증거 공백 계산
  → 부족한 증거 범주만 후속 검색
  → 출처 역할과 독립성 검증
  → 최종 문서 선정
```

### 권장 변경 우선순위

1. `tool_choice="required"`로 웹 검색 실행을 보장한다.
2. 조립된 검색어 하나 대신 원 질문과 구조화된 검색 맥락을 전달한다.
3. 출처별 하네스 호출을 질문별 통합 검색 세션으로 변경한다.
4. `user_location`에 한국 지역 정보를 제공한다.
5. 전체 검색 source 목록 반환을 활성화한다.
6. 검색 대상을 뉴스 기사에서 근거 문서 전체로 확장한다.
7. 충분성 판단을 Firecrawl 원문 확보 이후로 이동한다.
8. 문서 수가 아니라 증거 범주와 독립 출처 수로 종료를 판단한다.
9. 공식, 규제, 시장분석 증거가 부족할 때만 도메인 필터를 적용한다.
10. Firecrawl 스크랩 실패 URL에 제한적인 재시도를 적용한다.
11. 현재 지원되는 웹 검색 모델로 전환한다.
12. 라운드, citation과 스크랩 호출 수에 별도의 비용 상한을 둔다.

## 최종 정리

Phase 2 적용 후 SK브로드밴드 AI 검색 하네스는 출처별 검색 슬롯을 사용하지 않고, 질문 단위로 OpenAI 웹 검색을 실행한다.

현재 역할 분담은 다음과 같다.

```text
코드: 전체 출처 레지스트리 로드 + 비용 상한 + URL 귀속
AI: 원 질문 기반 최초 검색 + 제한적인 후속 검색어 생성
Firecrawl: 실제 원문 수집
후단 분석기: 최종 관련성 판단
```

기존 출처 플래너의 역할·신뢰도·도메인·증거 역량 메타데이터는 유지한다. 다만 AI 검색이 켜진 SK브로드밴드 경로에서는 `planned_sources` 최대 6개를 각각 검색하지 않는다. 전체 `registered_sources`는 발견 URL의 출처명과 신뢰도 등급을 귀속하는 데 사용한다. KOFIC PDF 같은 전용 수집기는 별도 경로로 계속 실행하고, AI 하네스가 꺼져 있으면 기존 출처별 Firecrawl 검색 경로를 그대로 사용한다.

OpenAI 웹 검색을 최우선으로 두려면 다음과 같이 바꾸는 것이 적절하다.

```text
AI: 질문 단위 검색 전략 + 검색어 + 증거 공백 판단
코드: 비용 상한 + 출처 신뢰도 + 원문 확보 + 종료 조건 + 추적성
Firecrawl: 실제 원문 수집
후단 분석기: 사실 검증 + 질문 관련성 최종 판단
```

이 구조가 OpenAI 웹 검색의 자율성을 살리면서도 TrendSparC의 핵심 원칙인 출처 추적성, 무조작, 비용 통제와 실패 추적성을 유지할 수 있다.
